# HookRelay
### Self-hosted Webhook Gateway

**Предметная область:** Сервис маршрутизации и гарантированной доставки вебхуков.

## О проекте
Сервис принимает вебхуки от сторонних API (GitHub, Stripe, Telegram), буферизует их и пересылает на серверы пользователя. Если целевой сервер недоступен, система делает повторные попытки отправки (ретраи) по заданным правилам.

---

## Функциональные требования и бизнес-правила

Ниже описана логика работы сервиса, на основе которой проектировалась БД.

* **Воркспейсы и пользователи:** Юзеры регистрируются по email. Проекты изолируются друг от друга через воркспейсы. В один воркспейс можно добавлять команду с разными ролями (owner, admin, member). Для работы по API генерируются ключи доступа с привязкой к воркспейсу.
* **Прием вебхуков:** Пользователь создает «источник» (Source) под конкретного провайдера и получает уникальный URL. При получении вебхука сохраняются сырые HTTP-заголовки, тело запроса (payload) в JSON, размер в байтах, IP и время. Для защиты от дублей пишется уникальный `idempotency_key` провайдера.
* **Маршрутизация:** Пользователь настраивает подписки (Subscriptions) — куда пересылать вебхуки. Можно фильтровать пересылку по типам событий (например, реагировать только на `push`).
* **Доставка и ретраи:** Для подписок задаются правила: макс. количество попыток, стартовая задержка и множитель времени. Каждая попытка дернуть сервер пользователя логируется (итоговый статус, HTTP-код, тело ответа, время ответа).
* **Мониторинг и алерты:** Ведется аудит действий юзеров (кто, что и когда изменил). Для отрисовки дашбордов раз в час собирается статистика по источникам (успешно/упало). Юзер может настроить алерты на падение процента успешных доставок.

## Архитектура БД и нормализация

Схема приведена к **3НФ**, названия таблиц и столбцов соответствуют конвенциям PostgreSQL (snake_case, множественное число, используются нативные типы вроде `uuid`, `jsonb`, `inet`).

Согласно требованиям ТЗ, явно указываю места, где нормализация была намеренно нарушена:

1. **Использование JSONB для сырых данных (отход от 1НФ).**
   Поля `events.payload`, `events.headers` и `audit_logs.changes` хранят данные с глубокой и произвольной вложенностью от сторонних сервисов. Раскладывать их по отдельным таблицам (EAV-модель) нецелесообразно — база ляжет от количества join-ов при чтении. Поэтому используем `jsonb`.

2. **Хранение вычисляемых агрегатов (отход от 3НФ).**
   В таблице `source_hourly_stats` лежат готовые счетчики (`events_count`, `failed_count`). По правилам 3НФ эти данные избыточны, так как их всегда можно высчитать через `SELECT COUNT() ... GROUP BY` из таблицы событий. Но при больших объемах вебхуков динамическая агрегация положит БД. Поэтому статистика считается фоном и пишется в отдельную таблицу (паттерн Rollup) для быстрой отдачи на фронт.
